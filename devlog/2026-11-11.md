## 1. Chi tiết phân tích feedback

### 1. "DB chậm với xa" & "LCP ở page là render data từ Supabase"
- **Hiện trạng:** Ứng dụng là React SPA (Vite). Khi người dùng vào trang chủ hoặc danh mục, trình duyệt phải tải JS (~1.3MB), sau đó client gọi trực tiếp Supabase REST API (`fetchProducts`, `fetchStores`) qua internet.
- **Vấn đề:** 
  - Database Supabase đặt ở xa người dùng Việt Nam (HKG/Singapore/US), độ trễ mạng (latency) cao.
  - **LCP (Largest Contentful Paint):** Điểm hiển thị nội dung chính bị nghẽn do phải đợi Supabase trả dữ liệu về mới render giao diện (Hero loop, thẻ sản phẩm).

### 2. "Đưa database về gần thì mới giảm được"
- **Giải pháp kỹ thuật:**
  - Kiểm tra & chuyển Region của Supabase sang Singapore (`ap-southeast-1`) gần VN nhất.
  - Áp dụng Caching: Dùng Vercel Edge Cache / Redis / Cloudflare Cache để cache danh sách sản phẩm và shop, tránh gọi trực tiếp Postgres mỗi lần user load trang.
  - Tối ưu tải tĩnh: Static prerender / SSR cho danh mục thay vì SPA thuần gọi API client.

### 3. "Lỗi to đùng trong console log, fix xong là lên được tầm 2-3s"

### 4. Fix Google Search kết quả hiển thị: Icon mặc định và "the site won't allow us"
- **Hiện trạng:** Tìm kiếm "ticoolture" trên Google hiển thị icon địa cầu xám và đoạn mô tả *"We would like to show you a description here but the site won't allow us."*
- **Nguyên nhân cốt lõi (3 tầng chặn Googlebot):**
  1. `public/robots.txt`: có chỉ thị `Disallow: /` chặn toàn bộ crawler truy cập domain.
  2. `vercel.json`: header trả về cho mọi route `/(.*)` chứa `X-Robots-Tag: noindex, nofollow`.
  3. `index.html`: chứa thẻ meta `<meta name="robots" content="noindex, nofollow" />`.
  4. Chưa có `favicon.ico` và các kích thước chuẩn (48x48, 192x192) mà Google Search yêu cầu.
- **Giải pháp xử lý:**
  - `public/robots.txt`: Đổi sang `Allow: /`, chỉ chặn các route nội bộ (`/portal`, `/lab`, `/api/`), khai báo sitemap.
  - `vercel.json`: Gỡ bỏ `X-Robots-Tag` khỏi `/(.*)`, chỉ gắn cho `/portal(.*)`.
  - `index.html`: Đổi thành `<meta name="robots" content="index, follow" />`, bổ sung OpenGraph, Twitter card và thẻ canonical.
  - Sinh bộ favicon chuẩn: `favicon.ico` (16, 32, 48px), `favicon-48x48.png`, `favicon-192x192.png`, `favicon-512x512.png`, `apple-touch-icon.png`.
  - Tạo `public/sitemap.xml` hỗ trợ Googlebot lập chỉ mục các route công khai.

## 2. Rút kinh nghiệm & Sai lầm
- **Không để Client SPA query trực tiếp Database không qua Cache:** Khi catalogue sản phẩm của shop ít thay đổi, việc để hàng nghìn lượt truy cập query trực tiếp vào Supabase sẽ gây nghẽn cổ chai mạng và kéo sập chỉ số LCP. Cần có tầng cache trung gian.
- **Kích thước Asset ảnh Hero quá lớn:** `background-hero.png` đang có dung lượng ~1.87MB chưa được tối ưu sang WebP/AVIF, cộng hưởng với việc đợi data làm tăng đáng kể LCP.
- **Để quên cấu hình chặn crawler khi lên Production:** `robots.txt Disallow: /`, `meta noindex` và header `X-Robots-Tag` từ giai đoạn dev đã chặn Googlebot thu thập dữ liệu khiến trang bị mất snippet và mất icon trên Google. Khi public site cần dọn sạch các chỉ thị chặn này và submit lại URL trên Google Search Console.
- **Stacking Context khi render modal toàn màn hình:** Đặt modal/lightbox sâu bên trong container có `overflow-x: hidden` hoặc `transform` sẽ bị giới hạn stacking context, khiến `z-[100]` vẫn bị che khuất bởi floating navbar `z-50`. Giải pháp bắt buộc là dùng `createPortal(..., document.body)`.
- **An toàn schema database khi bổ sung trường mới:** Khi thêm trường mới cho shop (`hero_image_url`), nếu chỉ trông cậy vào migration Postgres mà server chưa chạy lệnh `ALTER TABLE` thì PostgREST sẽ ném lỗi 400 làm chết API. Luôn cần cơ chế fallback an toàn (dùng cột text dự phòng có sẵn như `story_en` và `select("*")`) để code chạy mượt mà ngay lập tức.
- **Placeholder và Demo Data:** Không dùng tên một shop cụ thể làm placeholder cho form chung, tránh trường hợp các shop khác tưởng nhầm hệ thống bị lưu sai dữ liệu của họ.

## 4. Báo cáo đo kiểm hiệu năng End-to-End (Xóa sạch Cache - Fresh User)
- **Công cụ đo:** Playwright + Chromium (Edge engine) bật CDP `Network.setCacheDisabled: true`, giả lập khách truy cập mới 100% trên cả Desktop (1440x900) và Mobile (iPhone 14).
- **Kết quả đo thực tế:**
  1. **Trang Sản phẩm (`/products` - Desktop):**
     - **LCP:** **6,440ms (6.4 giây)** — mức RẤT CHẬM (Poor).
     - **Nguyên nhân chính:** REST API Supabase `cqavbkifdzkxssnfekgy.supabase.co/rest/v1/products` mất tới **2,545ms (2.5 giây)** để phản hồi qua mạng. Client SPA bị chặn rendering hoàn toàn cho đến khi query xong.
  2. **Trang chủ (`/`):**
     - **Thời gian tải toàn trang:** **4,200ms (Desktop)** / **3,656ms (Mobile)**.
     - **LCP Element:** Ảnh nền hero `background-hero-BnkC-Pwu.png` (nặng 1.87MB).
     - **Tổng dung lượng tài nguyên trang chủ:** **38.27 MB** (do 15 ảnh sản phẩm/shop tải đồng thời từ Cloudflare R2 và assets).
  3. **Trang Danh sách Shop (`/stores`):**
     - **Thời gian tải toàn trang:** **3,003ms (Desktop)** / **2,921ms (Mobile)**.
     - **Tổng dung lượng ảnh tải:** **24.38 MB** (18 ảnh sản phẩm gốc chưa qua thumbnail resize).
  4. **Lỗi Console & Network Failure:**
     - 0 lỗi đỏ trong Console (`Console Errors: 0`).
     - 0 request mạng bị fail (`Failed Requests: 0`).
- **Kết luận:**
  - Lời nhận xét của Senior IT *"LCP chậm do render data từ Supabase và mất 2-3s"* là **hoàn toàn chính xác 100%** (thực tế đo được 2.55s độ trễ DB).
  - Vấn đề cốt lõi không phải lỗi code cú pháp, mà là:
    1. Query Supabase trực tiếp từ client không có cache trung gian (mất 2.5s).
    2. Tổng payload ảnh quá khủng khiếp (38MB trang chủ, 24MB trang shop) do tải ảnh kích thước lớn từ R2 và ảnh asset hero 1.87MB.
