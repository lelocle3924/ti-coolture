## 2. Rút kinh nghiệm & Sai lầm

- **Xóa cache nhiều tầng khi có mutation dữ liệu tồn kho:**
  - *Vấn đề tiềm ẩn:* Tí Coolture sử dụng kiến trúc cache 2 tầng gồm Upstash Redis (`catalog:v1`) tại Edge và SWR cache (`memoryCache` + `sessionStorage`) tại trình duyệt. Nếu chỉ cập nhật DB mà không xóa key Redis và không invalidate client cache, người dùng thông thường sẽ vẫn thấy sản phẩm còn hàng trong tối đa 5-15 phút sau khi shop đã bấm hết hàng.
  - *Giải pháp:* Tại backend API `product-actions.ts`, luôn gọi `deleteCache("catalog:v1")` sau mỗi mutation thành công. Tại frontend Portal, gọi `invalidateClientCache("products")`.
- **Duy trì trần 12 Serverless Functions của Vercel Hobby:**
  - Thay vì tạo thêm file `api/portal/toggle-stock.ts`, gom action vào router hiện có `api/portal/product-actions.ts`. Đảm bảo hệ thống tuân thủ nghiêm ngặt giới hạn 12 endpoint mà không gây phát sinh chi phí hoặc lỗi deploy.
## 3. Tối ưu Hiệu năng & Trải nghiệm Shop Portal (Feature 003: `003-portal-speedup`)

### 1. Phân tích Nguyên nhân Gốc (Root Cause Analysis)
Từ đo lường thực tế trên môi trường live (`https://ticoolture.vn/portal`) qua Playwright:
1. **Frontend Double-Kill Waterfall (`loadPortalMe`):**
   - Sau mỗi thao tác mutation ("Lưu bản nháp", "Gửi duyệt", "Thu hồi yêu cầu"), frontend gọi `await loadPortalMe(token)`.
   - Vòng lặp tải lại toàn bộ thông tin shop, mạng xã hội, danh sách sản phẩm, ảnh và các yêu cầu chỉnh sửa khiến nút bấm bị block spinner tới 7 - 10 giây.
2. **Double API Call khi Mở Portal:**
   - Màn hình Portal gọi tuần tự `/api/portal/me`, đợi xong rồi mới gọi tiếp `/api/portal/save-shop` để lấy `pendingProfileRequest`.
3. **Overhead Xác thực JWT qua WAN:**
   - Mọi serverless function đều gọi `supabase.auth.getUser(token)` qua mạng WAN từ Vercel sang Supabase, tốn 250 - 500ms mỗi lượt.

### 2. Các Giải pháp Triệt để Đã Triển khai
1. **Eliminate Post-Mutation Full Reloads:**
   - Cập nhật `api/portal/save-draft.ts`: Trả về toàn bộ thực thể sản phẩm đầy đủ (bao gồm mảng `product_images` và metadata).
   - Cập nhật `src/views/Portal.tsx`:
     - `handleSaveDraft`: Merge sản phẩm trả về trực tiếp vào local state `products` và cập nhật form nháp mà **không** gọi `loadPortalMe`.
     - `handleSubmitReview`: Cập nhật trạng thái `pending_review` trực tiếp vào local state, chuyển view về `"list"`, triệt tiêu `loadPortalMe`.
     - `handleCancelEditRequest` & `handleCancelUploadRequest`: Cập nhật local state tức thì, loại bỏ `loadPortalMe`.
2. **Gộp Payload & Xóa Bỏ Waterfall `/api/portal/save-shop`:**
   - Đưa query `shop_profile_requests` vào khối `Promise.all` song song trong `api/portal/me.ts`.
   - Frontend `loadPortalMe` đọc trực tiếp `data.pendingProfileRequest` từ response của `/api/portal/me`. Xóa bỏ request tuần hoàn `/api/portal/save-shop`.
3. **Upstash Redis Auth Session Cache (TTL 60s):**
   - Trong `api/_lib/supabaseAuth.ts`: Hash token bằng SHA-256 (`auth_session:<hash>`), lưu cache 60s cho context shop/admin.
   - Thao tác lặp lại (toggle visibility, toggle stock) bỏ qua roundtrip xác thực Supabase Auth, giảm độ trễ từ ~600ms xuống ~120 - 165ms.
4. **Resilient Schema Column Handling:**
   - Tối ưu truy vấn `products` không cố định các cột chưa có trong live DB schema (`reject_reason`, `is_out_of_stock`).
   - Xử lý fallback sạch bằng Javascript, đảm bảo 0 lỗi runtime 42703 trên live Supabase.

## 4. Bài học & Rút kinh nghiệm Bổ sung

1. **Sai lầm giả định Schema Database đã có cột mới:**
   - *Vấn đề:* Code `save-draft.ts` và `me.ts` ban đầu thêm `reject_reason` và `is_out_of_stock` trực tiếp vào câu `select(...)` của Supabase vì đã có migration file trong repo. Tuy nhiên, trên live Supabase PostgreSQL, migration chưa được chạy thủ công qua SQL Editor, dẫn đến lỗi PostgREST `42703 (column does not exist)`.
   - *Hậu quả:* Danh sách sản phẩm của shop bị rỗng (`[]`) hoặc API trả về lỗi 500.
   - *Bài học:* Luôn kiểm tra schema thực tế của live database trước khi đưa cột mới vào câu lệnh `select(...)`. Cung cấp lớp bọc fallback an toàn ở application layer để code vẫn chạy mượt mà ngay cả khi database chưa kịp chạy migration.
2. **Không gọi API làm mới toàn bộ trang sau mỗi mutation nhỏ:**
   - *Bài học:* UI hiện đại phải sử dụng Local State Merging hoặc Optimistic UI. Khi backend mutation trả về thực thể vừa cập nhật, frontend chỉ việc thay thế hoặc bổ sung phần tử đó vào local state mảng `products`. Việc gọi lại toàn bộ `/api/portal/me` là nguyên nhân số 1 làm tê liệt trải nghiệm của đối tác shop.
3. **Cấm dùng từ "xưởng":**
   - Tiếp tục quán triệt tuyệt đối dùng thuật ngữ "shop", không dùng từ "xưởng" trong bất kỳ thông báo, biến, comment hoặc tài liệu nào.
